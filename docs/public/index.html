Sealed mode

One boundary, brokered by the host

The agent loop, its tools and its files run in the sandbox. Keys, secrets, egress, approvals and the token budget stay on the host.

No API key in the boxToken budget on the hostAudit and approvals on the host
Principles

Small surface, safe defaults

/one-way

One Config, one NewTool, one Run / Stream. No module registry, no presets, no second constructor.

/secure-default

Shell and HTTP refuse to exist without allowlists. Secrets never reach the model. Every redirect is re-validated.

/durable

A run can pause for a person, persist in the session, and resume in another process, including inside a sealed box.

/batteries

A2A, MCP, evals, OTel, triggers, memory, skills, graph and swarm, as small packages rather than a platform.

Installation

Add kritrim to a Go module, confirm the toolchain, then move on to the quickstart. There are no third-party dependencies to vendor.

1. Check Go

kritrim needs Go 1.27 or newer. On build servers, prefer 1.27.4 or later for the net/http fix GO-2026-6859.

go version

2. Add the module

From any module that will import kritrim:

go get github.com/ganeshdipdumbare/kritrim@v1.0.0

That pulls the stable v1 API. MIT licensed; see LICENSE.

3. Optional CLI binaries

Release builds of kritrim, kritrim-evals and kritrim-vmagent ship on the releases page with a Sigstore-signed SHA256SUMS and build provenance. SECURITY.md shows how to verify them. You only need these for evals CLI work or Firecracker guest images — not for importing the SDK.

Try it offline from a checkout

Every example in the repository compiles against the mock model, so you can clone and run without an API key:

git clone https://github.com/ganeshdipdumbare/kritrim
cd kritrim
go test ./...
go run ./examples/quickstart

You should see a short hello from the mock model printed to the terminal.

Versioning

Within v1 nothing exported is removed or changed, interfaces you implement gain no methods, and stored sessions, audit logs and traces stay readable. docs/API.md spells out the promise; CI checks it. Coming from v0.9? Read docs/MIGRATING.md. Every change is in the changelog.

Quickstart

This guide takes you to a first running agent: create a module, pick a model provider, run a prompt, then give the agent a typed tool. Streaming and saved conversations come after. Everything beyond that has its own guide, linked at the end.

1. Create a module

Start from an empty folder (or use the repo’s examples/quickstart if you cloned it):

mkdir hello-agent && cd hello-agent
go mod init example.com/hello-agent
go get github.com/ganeshdipdumbare/kritrim@v1.0.0

2. Pick a model provider

The model is one value you hand to kritrim.New. The rest of your code stays the same no matter which provider is behind it. Pick the tab for a provider you already have access to, set the env var, then create main.go with that snippet.

Set a key, then create main.go:

export ANTHROPIC_API_KEY=sk-ant-...
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/ganeshdipdumbare/kritrim"
)

func main() {
	a, err := kritrim.New(kritrim.Config{
		Model:        kritrim.Anthropic("claude-sonnet-5-5"),
		Instructions: "You are concise.",
	})
	if err != nil {
		log.Fatal(err)
	}
	defer a.Close()

	res, err := a.Run(context.Background(), "What is an agent, in one sentence?")
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println(res.Text)
}

4. Add a typed tool

You now have a working agent loop, but the agent has nothing to act with — it can only answer from what the model already knows. A tool is a Go function the model can decide to call. The schema is derived from the argument type; you never hand-write JSON Schema for a typed tool.

Replace your agent setup with this (keep the same Model line from your provider tab, or use the mock turns below to stay offline):

func weather(ctx context.Context, in struct {
	City string `json:"city" desc:"city name"`
}) (string, error) {
	return "18C and light rain in " + in.City, nil
}

func main() {
	a, err := kritrim.New(kritrim.Config{
		Model: kritrim.Mock(
			kritrim.TurnTool("weather", map[string]any{"city": "Lisbon"}),
			kritrim.Turn{Text: "It is raining in Lisbon."},
		),
		Tools: []kritrim.Tool{
			kritrim.NewTool("weather", "Get the weather", weather),
		},
	})
	if err != nil {
		log.Fatal(err)
	}
	defer a.Close()

	res, err := a.Run(context.Background(), "What is the weather in Lisbon?")
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println(res.Text)
}

Run it again. With the mock model you will always get the scripted tool call and final text. With a live model, it should choose weather, pass city, and answer from the tool result. A string result goes to the model as-is; any other return type is JSON-encoded.

What just happened

New builds an agent from a config. Run sends your prompt, lets the model call tools in a loop, and returns a Result with the final text, the steps taken, token usage and a stop reason. Breaking out of Stream early cancels the run and cleans up — covered next.

5. Stream events (optional)

When you want tokens as they arrive — or to watch tool calls live — use Stream instead of Run. It returns an iter.Seq2; breaking the loop cancels the run.

for e, err := range a.Stream(ctx, "Plan a weekend in Lisbon") {
	if err != nil {
		break
	}
	switch e.Type {
	case kritrim.EventText:
		fmt.Print(e.Text)
	case kritrim.EventToolCall:
		fmt.Println("→", e.ToolCall.Name)
	case kritrim.EventToolResult:
		fmt.Println("←", e.ToolResult.Content)
	}
}

Event type strings are named constants (EventText, EventToolCall, …). Full event list: Streaming.

6. Save a conversation (optional)

Without a session store, every Run starts fresh. Point Config.Session at a store and pass the same Thread id to continue a conversation:

a, err := kritrim.New(kritrim.Config{
	Model:   model, // the Model value from your provider tab
	Session: kritrim.FileSessions(".agent/sessions"),
})
if err != nil {
	log.Fatal(err)
}
defer a.Close()

ctx := context.Background()
a.Run(ctx, "My name is Ada.", kritrim.Thread("user-42"))
res, _ := a.Run(ctx, "What is my name?", kritrim.Thread("user-42"))
fmt.Println(res.Text) // remembers Ada

Concepts

These are the words the rest of the docs use. Skim once after the quickstart; come back when a guide names something new.

The loop in one picture

You call Run (or Stream). kritrim sends the prompt to the model. If the model asks for tools, kritrim runs them (after schema checks, policy and any approval), feeds the results back, and repeats until the model answers or a stop condition hits. That whole cycle is one run; each model round-trip inside it is a step.

TermWhat it is
AgentWhat kritrim.New(Config) returns: a model, tools, hooks, a session store and an optional sandbox.
RunOne Run or Stream call. It ends with a Result: text, steps, usage, stop reason and interrupts.
StepOne model call inside a run, plus the tool calls that call asked for.
ToolA typed Go function with a name, a derived JSON Schema and a result. Built-ins and MCP tools look the same to the model.
SessionA conversation stored under an id (Thread("id")), including paused approvals and a small state bag.
HookA callback around the run, a model call or a tool call. Hooks can observe and shape; built-in security hooks run first.
ApprovalA risky tool asks Config.Approve before it runs. The decision can be synchronous or a durable pause.
InterruptA paused approval with a stable id. Resume later with Decisions.
SandboxWhere shell and file tools run: Docker, Local (dev only), SSH, or a cloud / microVM adapter.
SealedThe whole agent process runs inside a sandbox. The host keeps the keys and brokers model calls, secrets, tools, audit and approvals.
BrokerThe one path built-in tools use for network, processes and files. It enforces allowlists, SSRF checks and redaction.

Providers

This guide shows how to pick a model, set credentials, tune reasoning and guardrails, and fall back when a call fails. A model is one value; the agent loop does not care which constructor made it.

1. Choose a constructor

Each constructor reads its API key from the environment unless you pass ModelConfig.APIKey. Set the env var before you run:

kritrim.OpenAI("gpt-4.1")                       // OPENAI_API_KEY
kritrim.OpenAIResponses("gpt-5")                // Responses API, same key
kritrim.Anthropic("claude-sonnet-5-5")          // ANTHROPIC_API_KEY
kritrim.Gemini("gemini-2.5-pro")                // GEMINI_API_KEY
kritrim.Bedrock("anthropic.claude-sonnet-5-5")  // AWS SigV4 + region
kritrim.Ollama("llama3")                        // localhost:11434, no key
kritrim.DeepSeek("deepseek-chat")               // DEEPSEEK_API_KEY
kritrim.Groq("llama-3.3-70b-versatile")         // GROQ_API_KEY
kritrim.Mistral("mistral-large-latest")         // MISTRAL_API_KEY
kritrim.OpenRouter("anthropic/claude-sonnet-5-5") // OPENROUTER_API_KEY
kritrim.LiteLLM("http://gateway:4000", "gpt-4.1")
kritrim.Compatible("provider", "https://host/v1", "model")
kritrim.Mock(kritrim.Turn{Text: "offline"})

Bedrock uses the default AWS credential chain and AWS_REGION or AWS_DEFAULT_REGION.

2. Point at a gateway (optional)

Pass ModelConfig for a custom base URL, headers or timeout:

model := kritrim.OpenAI("gpt-4.1", kritrim.ModelConfig{
	BaseURL: "https://gateway.internal/v1",
	Headers: map[string]string{"X-Team": "support"},
	Timeout: 2 * time.Minute,
})

3. Turn on reasoning

One Reasoning setting maps across five providers (Anthropic extended thinking, OpenAI reasoning_effort, Responses, Gemini thinkingConfig, Bedrock reasoning_config):

a, err := kritrim.New(kritrim.Config{
	Model:     kritrim.Anthropic("claude-sonnet-5-5"),
	Reasoning: &kritrim.Reasoning{Effort: "high"}, // low | medium | high
})

Budget sets the thinking-token allowance exactly; effort levels map to 1024, 4096 and 16384. Include: true streams thinking as reasoning events where the provider returns it.

Thinking tokens are output tokens

They count against MaxOutputTokens and the run's budget. A budget that cannot hold the thinking allowance is refused before the call. Anthropic requires thinking blocks (with signature) before a tool result — kritrim keeps and replays them.

4. Attach a guardrail

On Bedrock the guardrail runs inside Converse. For any model, guard.Bedrock calls ApplyGuardrail and fails closed. Needs AWS credentials that can invoke the guardrail.

model := kritrim.Bedrock("anthropic.claude-sonnet-5-5", kritrim.ModelConfig{
	Guardrail: &kritrim.Guardrail{ID: "gr-123", Version: "1"},
})

hooks, err := guard.Bedrock(guard.BedrockConfig{ID: "gr-123", Version: "1", Tools: true})

Other providers refuse ModelConfig.Guardrail at New. When a provider safety system blocks a reply, the run ends with StopGuardrail and that reply's tool calls do not run.

5. Route and fall back

Route chooses a model up front. Fallback reacts after failure. They compose, and the audit log records the model actually used.

a, err := kritrim.New(kritrim.Config{
	Model: small,
	Route: func(ctx context.Context, prompt string) kritrim.Model {
		if len(prompt) > 500 {
			return large
		}
		return nil // nil means Config.Model
	},
	Fallback: []kritrim.Model{kritrim.OpenAI("gpt-4.1")},
	Retry:    &kritrim.Retry{Max: 3},
})

Tools

This guide takes you to a working typed tool: derive a schema from a Go struct, register it on an agent, then layer parallel calls, risky approvals and the built-ins (HTTP, shell, files, Python…). Credentials stay on the process that constructs the agent — tools never need your model API key.

1. Define a typed tool

The schema comes from the argument type. Tags drive the JSON the model sees: json for names, desc for help text, enum for allowed values. omitempty or a pointer makes a field optional. You never hand-write JSON Schema for a typed tool.

type SearchIn struct {
	Query string `json:"query" desc:"what to look for"`
	Limit int    `json:"limit,omitempty" desc:"max results"`
	Sort  string `json:"sort,omitempty" enum:"relevance,date"`
}

search := kritrim.NewTool("search_tickets", "Search support tickets",
	func(ctx context.Context, in SearchIn) ([]Ticket, error) {
		return db.Search(ctx, in.Query, in.Limit)
	})

a, err := kritrim.New(kritrim.Config{
	Model: model, // same Model value as in Quickstart / Providers
	Tools: []kritrim.Tool{search},
})
if err != nil {
	log.Fatal(err)
}
defer a.Close()

A string result goes to the model as-is; any other return type is JSON-encoded. A returned error becomes an error tool result so the model can recover. The callable itself is not exported — NewTool is the only way to define a typed tool.

What just happened

kritrim derived a JSON Schema from SearchIn, registered the tool on the agent, and will validate every model-supplied argument against that schema before your function runs.

2. Understand validation

Arguments are checked for typed, raw and MCP tools alike: types, required fields, enum/const, unknown fields, string length and pattern, numeric ranges, array sizes, anyOf/oneOf/allOf/not and local $ref. A schema keyword that cannot be enforced (a remote $ref, if/then, patternProperties…) makes the call fail instead of passing unchecked.

3. Run tools in parallel

One model step can ask for several tools. ToolConcurrency runs safe tools together; risky tools always stay sequential so approvals keep their order.

a, err := kritrim.New(kritrim.Config{
	Model:           model,
	Tools:           tools,
	ToolConcurrency: 4,
})

4. Call a tool yourself

When you want the same validation path without a model turn — tests, UIs, or a manual retry — use CallTool:

out, err := a.CallTool(ctx, "search_tickets", map[string]any{"query": "refund"})

5. Use a dynamic schema (optional)

MCP servers and simulators often bring a schema that did not come from a Go struct. NewRawTool takes that schema and a map[string]any handler:

t := kritrim.NewRawTool("lookup", "Look up a record", schema,
	func(ctx context.Context, args map[string]any) (string, error) {
		return lookup(ctx, args)
	})

6. Mark a tool as risky

Wrap with kritrim.Risky so the agent asks Config.Approve before the call. Details and durable pauses: Approvals.

Tools: []kritrim.Tool{kritrim.Risky(refund)}

7. Add built-in tools

Built-ins go through the same broker as your tools. Constructing one is the grant: HTTP and shell refuse an empty allowlist; files are read-only unless Write: true. No separate credentials file — use env vars or Config.Secrets for values tools resolve via secret://.

kritrim.Time()
kritrim.HTTP(kritrim.HTTPConfig{AllowHosts: []string{"api.example.com"}})
kritrim.WebFetch(kritrim.WebFetchConfig{AllowHosts: []string{"*.wikipedia.org"}})
kritrim.WebSearch(kritrim.WebSearchConfig{})
kritrim.Shell(kritrim.ShellConfig{Allow: []string{"go", "git"}})
kritrim.Files(kritrim.FilesConfig{Root: "./work", Write: true})
kritrim.Read(kritrim.ReadConfig{Root: "."})
kritrim.Write(kritrim.WriteConfig{Root: "./out"})
kritrim.EditFile(kritrim.EditConfig{Root: "."})
kritrim.Python(kritrim.PythonConfig{})   // needs Config.Sandbox
kritrim.Todos()
kritrim.Notebook()
kritrim.Sleep(30 * time.Second)
kritrim.Stop()
kritrim.AskUser()

Web fetch

WebFetch is HTTP for reading: one GET, with HTML turned into readable text. Use HTTP when the model needs methods, headers and the exact response; use WebFetch when it needs to read a page. A page that builds its content in the browser comes back nearly empty — there is no DOM and no JavaScript.

A page is data, not instructions

Fetched text reaches the model as a tool result. A page that says "ignore your instructions" is a page saying so, not a user asking. Keep the allowlist as narrow as the task.

Todos

A long task drifts: the model finishes step two, forgets steps four and five, and declares victory. Todos keeps the plan in session state so it survives a pause, a resume and a restart. Put "keep the todo list current" in Instructions; the tool stores a plan, it does not enforce one.

Python in a sandbox

This is the one built-in whose argument cannot be checked: an allowlist constrains a command, and Python is a language. It is risky, requires Config.Sandbox (or sealed mode), and refuses to run on the host unless you set AllowUnsafeHost. The code reaches the interpreter on stdin — no shell, nothing to quote. Docker must be available if you use the Docker sandbox.

a, err := kritrim.New(kritrim.Config{
	Model:   model,
	Tools:   []kritrim.Tool{kritrim.Python(kritrim.PythonConfig{})},
	Sandbox: kritrim.Docker(kritrim.DockerConfig{Image: "python:3.13-slim"}),
	Approve: approve,
})

Streaming

This guide takes you from a blocking Run to live events: stream text deltas, watch tool calls, and cancel cleanly when the consumer stops reading. No extra credentials — use the same agent and model as in the quickstart.

1. Stream instead of Run

Stream returns an iter.Seq2. Breaking out of the loop cancels the run and cleans up in-flight work. Use the same context.Context and prompt options you would pass to Run.

for e, err := range a.Stream(ctx, "A haiku about Lisbon") {
	if err != nil {
		break
	}
	if e.Type == kritrim.EventText {
		fmt.Print(e.Text)
	}
}

You should see tokens print as they arrive (or one chunk on providers that only deliver a single delta).

What just happened

The agent loop ran the same way as Run, but each step emitted typed events instead of waiting for a finished Result. Leaving the range early cancelled that run.

2. Handle the event types

Every type is a named constant (kritrim.EventText, EventToolCall, …, EventInterrupt). Columns below are the event type string and the fields filled on that event:

	if err != nil {

	switch e.Type {
	case kritrim.EventText:

	case kritrim.EventToolCall:

	case kritrim.EventToolResult:
		fmt.Println("←", e.ToolResult.Content)
	}
}

3. Read the stop reason

When you need a finished Result instead of an iterator, keep using Run. Its Result.Stop uses the same family of constants: StopDone, StopMaxSteps, StopInterrupt, StopStopped, StopHook, StopGuardrail.

res, err := a.Run(ctx, "hello", kritrim.OnEvent(func(e kritrim.Event) {
	if e.Type == kritrim.EventText {
		fmt.Print(e.Text)
	}
}))

Sessions and state

This guide takes you to a conversation that survives restarts: pick a session store, pass a thread id, then use state, fork, cancel and optional signed history. No cloud credentials are required for file or memory stores; SQL needs a database you already configure.

1. Attach a session store

Without a store, every Run starts fresh. Point Config.Session at a store and pass the same Thread id to continue:

a, err := kritrim.New(kritrim.Config{
	Model:   model,
	Session: kritrim.FileSessions(".agent/sessions"),
	// or kritrim.MemorySessions(), kritrim.SQLSessions(db, cfg)
})
if err != nil {
	log.Fatal(err)
}
defer a.Close()

a.Run(ctx, "My name is Ada.", kritrim.Thread("user-42"))
res, _ := a.Run(ctx, "What is my name?", kritrim.Thread("user-42"))
fmt.Println(res.Text) // remembers Ada
What just happened

The first run saved the turn under user-42. The second run loaded that history, sent it with the new prompt, and saved again. The store is version-checked so two writers cannot silently overwrite each other.

2. Read and write session state

Tools and hooks share a small key-value bag on the session. It is saved with the conversation and never sent to the model:

kritrim.StateFrom(ctx).Set("seen", true)
v := kritrim.StateFrom(ctx).Get("seen")

3. Fork, cancel and idempotency

Fork snapshots a thread (including paused approvals). Cancel stops a run you started with a known id. Idempotency keys make a prompt safe to retry:

a.Fork(ctx, "user-42", "user-42-experiment") // snapshot, including paused state
a.Cancel("run-7")                            // stop a run started with kritrim.RunID("run-7")
res, _ := a.Run(ctx, "charge", kritrim.Idempotency("order-1234"))
Conflict

If another process saved the session first, Save returns ErrSessionConflict. Reload and retry; the run never silently loses a turn.

4. Sign history (optional)

Message history is an instruction channel. An agent replays whatever the store returns, so write access to a shared Redis, a wide DB grant or a mounted volume is write access to the user's instructions. Keep the HMAC key out of the store it protects — load 32+ random bytes from a KMS or secret manager.

key := loadKeyFromKMS() // 32+ random bytes, kept out of the store it protects
a, err := kritrim.New(kritrim.Config{
	Model:   model,
	Session: kritrim.SignedSessions(kritrim.FileSessions(".agent/sessions"), key),
})

_, err = a.Run(ctx, "continue", kritrim.Thread("user-42"))
if errors.Is(err, kritrim.ErrSessionTampered) {
	// someone edited the stored conversation; nothing was replayed
}

Every save is HMAC-SHA256 over the thread id, the messages, the state and any pending approval. A load that does not match is refused, and so is a record with no signature at all.

Content, not freshness

The signature catches an edit. It does not catch a deleted session or a rollback to an older signed copy. To migrate a store with unsigned sessions, read each through the plain store and save it once through the signed one.

Context management

This guide takes you to a long conversation that stays inside a token budget: configure ContextConfig, pick a strategy, and optionally estimate tokens yourself. Compaction only changes what is sent to the model — the session store keeps the full history on disk.

1. Set a context budget

You need a session store so history exists across turns. Then set MaxTokens, how many recent messages to keep, and a strategy. No extra API key is required for KeepWindow; SummarizeWith needs a model (often a smaller, cheaper one) with its own credentials.

a, err := kritrim.New(kritrim.Config{
	Model:   model,
	Session: kritrim.FileSessions(".agent/sessions"),
	Context: &kritrim.ContextConfig{
		MaxTokens: 60_000,
		KeepLast:  30,
		Strategy:  kritrim.SummarizeWith(small, ""), // or KeepWindow(), Summarize(fn)
	},
})

With no ContextConfig the whole history is sent on every step until the provider's own limit. With one, nothing happens while the history fits; once it goes over MaxTokens, the strategy decides what the call sends.

What just happened

On each model call the run estimates history size. Over budget, the strategy returns a shorter message list for that call only. The stored session still has every turn.

2. Pick a strategy

Columns: strategy constructor, what the model receives when compaction runs, and the cost of that choice. KeepLast defaults to 20.

StrategyWhat it sendsCost
KeepWindow() (default)the system prompt and the last KeepLast messagesno model call
SummarizeWith(model, instructions)a summary of what was dropped, then the recent messagesone call to model, usually a small one
Summarize(fn)whatever your function returns in place of the dropped messagesyours

Use KeepWindow when old turns stop mattering (support chat). Use SummarizeWith when an early decision still matters thirty turns later.

3. Write your own strategy (optional)

Compact gets the full history and returns the messages to send. It must return a valid conversation: a tool result cannot come first, and every tool result it keeps needs the assistant turn that asked for it. The built-in strategies never orphan a tool result.

type Strategy interface {
	Compact(ctx context.Context, msgs []Message, cfg ContextConfig) ([]Message, error)
}

4. Estimate tokens

This is the same estimate the run's token budget uses: about four characters per token plus a small per-message overhead. No network call and no tokenizer. Within about 10% for English prose; under-counts dense JSON, so leave headroom.

n := kritrim.EstimateTokens(msgs)
The session keeps everything

A strategy only changes what is sent to the model. Change the strategy later and the next run can see the old turns again.

Approvals

This guide takes you to gated tool calls: wrap a tool as risky, approve synchronously in a CLI, then pause and resume hours later from another process. Durable pauses need a session store; the same pattern works in sealed mode.

1. Mark the tool and set Approve

Only tools wrapped with kritrim.Risky ask for approval. Your Approve callback runs before the tool body. No extra credentials — this is process-local unless you persist via sessions.

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: []kritrim.Tool{kritrim.Risky(refund)},
	Approve: func(ctx context.Context, req kritrim.Approval) (kritrim.Decision, error) {
		fmt.Println(req.Message)
		return kritrim.Approve(), nil // or Reject, Edit, Respond
	},
})
What just happened

When the model called the risky tool, kritrim paused the tool path, invoked your callback, and only then ran the tool (or rejected / edited arguments / responded).

2. Pause for a human (durable)

Return Pause(). The run saves the pending step with the session and returns interrupts. Attach Config.Session and pass a Thread so another process can resume later.

Approve: func(ctx context.Context, req kritrim.Approval) (kritrim.Decision, error) {
	return kritrim.Pause(), nil
},

res, _ := a.Run(ctx, "Refund A-17", kritrim.Thread("ticket-981"))
// res.Stop == "interrupt"; res.Interrupts[0].ID

// Later, in another process with the same session store:
res, _ = a.Run(ctx, "", kritrim.Thread("ticket-981"),
	kritrim.Decisions(map[string]kritrim.Decision{
		res.Interrupts[0].ID: kritrim.Approve(),
	}))

3. Know the resume rules

  • The model is not called again on resume; only the remaining tools run.
  • A second resume gets ErrSessionConflict, so a tool runs once.
  • A paused thread refuses a new prompt until the interrupts are answered.
  • This works in sealed mode: pending state crosses the RPC boundary and survives a box restart.

Structured output

This guide takes you from free-text answers to a filled Go struct: declare a type with the same tags as tools, pass Output on the run, and handle one repair round or ErrOutput. Uses the same model credentials as your agent.

1. Declare the type

Use json, desc and optional fields the same way you would for a tool argument. The schema is derived from those tags.

type Trip struct {
	City    string   `json:"city"`
	Packing []string `json:"packing" desc:"things to pack"`
	Budget  int      `json:"budget_eur,omitempty"`
}

2. Ask the run to fill it

Pass a pointer with kritrim.Output. On success the struct is populated; on failure after one repair round you get kritrim.ErrOutput.

var trip Trip
_, err := a.Run(ctx, "Plan Lisbon", kritrim.Output(&trip))
if err != nil {
	// kritrim.ErrOutput after one repair round
	log.Fatal(err)
}
fmt.Println(trip.City, trip.Packing)
What just happened

kritrim asked the provider for structured JSON (or a forced tool, depending on the model), decoded into Trip, and repaired once if the first payload failed validation.

3. Know how providers map

OpenAI and Gemini use native JSON schema; Anthropic and Bedrock get a forced tool; OpenAI-compatible providers can use JSON mode. Your call site stays the same — only the transport differs.

Security

This guide takes you through the defaults that already protect every agent, then shows how to set run limits, wire secrets, redact PII and steer with hooks. Enabling a built-in capability is the grant — there is no second policy file to drift from the code.

1. Rely on the defaults

You do not turn security on with a flag. Constructing a tool is the permission. Scan these defaults before you add shell, HTTP or files:

Default deny

HTTP and Shell refuse to be constructed without an allowlist. Files is read-only unless Write: true.

SSRF and rebinding

Exact allowlisted hosts may be private; wildcard hosts must be public, checked at dial time on the IP actually connected to, so DNS rebinding cannot reach an internal address. Every redirect is re-validated.

Secrets

secret://NAME resolves at use and is redacted from output, events and audit. A request that carries a secret never follows a redirect to another host. Sealed boxes get random placeholders only.

No inherited credentials

Shell commands, MCP stdio servers and local boxes start with a minimal environment (PATH, HOME, locale, temp dir). Your API keys never reach them; pass extras with ShellConfig.Env or MCPConfig.Env.

Symlink-safe files

File tools open their root with os.Root: a symlink inside the root cannot read or write outside it.

Validated arguments

Tool arguments are checked against the tool schema before the call, so a model cannot pass types, values or fields the tool did not declare.

Guardrails

A Bedrock guardrail can screen every call, inside Converse or for any model with guard.Bedrock. A blocked reply ends the run with StopGuardrail and its tool calls never run.

Audit

One hash-chained JSON line per model, tool and approval. With AuditKey the chain is HMAC-signed and a signed head detects truncation.

2. Set limits, audit and secrets

Put secret values in Config.Secrets (or the environment your process already uses). For a signed audit log, load 32+ random bytes from a KMS — not from a file next to the log.

a, err := kritrim.New(kritrim.Config{
	Model:  model,
	Limits: kritrim.Limits{Steps: 20, ToolCalls: 50, Tokens: 200_000},
	Audit:  kritrim.AuditFile(".agent/audit.jsonl", kritrim.AuditKey(auditKey)),
	Secrets: map[string]string{"GITHUB_TOKEN": os.Getenv("GITHUB_TOKEN")},
})

Defaults: 20 steps, 100 tool calls and kritrim.DefaultTokenLimit (1,000,000) tokens per run. Set Tokens: -1 to remove the token cap. The token budget is checked before every model call, including the structured-output repair call. In sealed mode the host enforces the run's Limits.Tokens as well as Sealed.MaxTokens.

What just happened

Every model and tool step now counts against your caps, secret references resolve only at use, and each action appends a tamper-evident audit line.

3. Add redaction and deny policies

Put guards first in the chain so tracing sees redacted values. kritrim.Chain runs hooks in order; a Before hook that errors or denies stops the chain.

deny, _ := guard.Deny(`(?i)ignore all previous`, "prompt injection")
a, err := kritrim.New(kritrim.Config{
	Model: model,
	Hooks: kritrim.Chain(deny, guard.PII("email", "credit_card"), trace.OTel(otelCfg)),
})

4. Steer with hooks

A hook can ask for another answer, reroute a tool call, or end the run without forking the loop:

Hooks: kritrim.Hooks{
	AfterModel: func(ctx context.Context, e *kritrim.ModelEvent) {
		if strings.Contains(e.Response.Text, "TODO") {
			e.Retry = true // capped by Retry.Max
		}
	},
	BeforeTool: func(ctx context.Context, e *kritrim.ToolEvent) error {
		if e.Call.Name == "web_search" {
			e.Swap = "internal_search"
		}
		return nil
	},
	AfterTool: func(ctx context.Context, e *kritrim.ToolEvent) {
		if e.Result.IsError {
			e.End = "tool failed" // Result.Stop == StopHook
		}
	},
}

A swapped call goes through approval, argument validation and BeforeTool again, so a swap cannot skip a check, and it cannot swap a second time.

Trust boundary

The broker governs built-in tools. Your own Go tools are code you compiled into the binary. Put untrusted work in a sandbox.

Authorization

This guide takes you to per-caller tool policy: build a Cedar-style policy, attach it as hooks, and pass user and roles on each run. Config.Tools answers "may this agent refund"; policy answers "may this caller refund this much". No separate policy service — rules live in Go next to the agent.

1. Build and attach a policy

Import github.com/ganeshdipdumbare/kritrim/authz. Put policy.Hooks() first in kritrim.Chain so a denied call never reaches tracing as if it ran.

import "github.com/ganeshdipdumbare/kritrim/authz"

policy, err := authz.New(
	authz.Permit("*").For("admin"),
	authz.Permit("current_time", "web_*"),
	authz.Permit("refund").For("support").
		When(func(r authz.Request) bool { return r.Number("amount") <= 100 }).
		Because("support may refund up to 100 euros; ask a manager for more"),
	authz.Forbid("shell"),
)
if err != nil {
	log.Fatal(err)
}

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: tools,
	Hooks: policy.Hooks(),
})
a.Run(ctx, "refund order A-17", kritrim.User("u-7"), kritrim.Roles("support"))
What just happened

On each tool call the policy saw the run's user and roles plus the model-chosen arguments (after any approval edit). A forbid or missing permit blocked the call and told the model why.

2. Learn the three rules

The semantics are Cedar's:

  1. An explicit Forbid beats every Permit.
  2. Otherwise, one matching Permit is enough.
  3. With nothing matching, the call is denied.

Default deny is the point. Adding a tool to an agent does not quietly widen what every caller can reach, and a typo in a policy fails closed.

3. Narrow with builders

Columns: policy piece and what it constrains. Identity comes from kritrim.User / kritrim.Roles (or Config.User / Config.Roles).

PieceNarrows the policy to
Permit(tools...), Forbid(tools...)these tool names; * and web_* match with path.Match
.For(roles...)callers with one of these roles
.By(users...)these user ids
.When(fn)calls the condition accepts; read arguments with r.Number, r.Text, r.HasRole
.Because(text)sets what the model is told when this policy denies

Conditions see arguments after any approval edited them — ceilings and path prefixes belong here. A condition that panics denies the call instead of crashing the run.

4. Treat denial as a message

The run keeps going. The model is told the call was blocked and why, and usually explains the limit to the user. Write Because for the model to read. To check a decision outside a run (grey out a button), call policy.Check(authz.Request{...}); it returns nil when allowed and an error wrapping authz.ErrDenied when not.

Policy can only narrow

Policy runs after kritrim's own checks. It cannot grant Shell a command its allowlist lacks, and it cannot waive an approval.

Sandboxes

This guide takes you to shell and file tools that run off the host: Docker first, then attach/stream, SSH, and cloud or microVM adapters. Docker needs a local daemon; cloud adapters need their own API keys in the environment; Firecracker needs Linux with KVM.

1. Point tools at a sandbox

Set Config.Sandbox. Shell and file tools execute inside the machine the sandbox opens. Your model API key stays on the host process.

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: []kritrim.Tool{
		kritrim.Shell(kritrim.ShellConfig{Allow: []string{"go", "git"}}),
		kritrim.Files(kritrim.FilesConfig{Root: "/workspace"}),
	},
	Sandbox: kritrim.Docker(kritrim.DockerConfig{Image: "golang:1.27"}),
})
What just happened

When the model called shell or files, kritrim opened a Docker machine, ran the command inside it under the allowlist, and streamed results back to the loop.

2. Harden the container

Containers kritrim creates drop every Linux capability, set no-new-privileges, have no network, and are capped at 2 GB of memory, 2 CPUs and 512 processes. Tighten or relax per sandbox:

kritrim.Docker(kritrim.DockerConfig{
	Image:     "golang:1.27",
	User:      "1000:1000", // recommended: not root
	ReadOnly:  true,        // read-only root, writable /tmp
	Memory:    "1g",        // "none" removes the cap
	CPUs:      "1",
	PidsLimit: 256,         // -1 removes the cap
	CapAdd:    nil,         // re-add capabilities only if needed
})

An attached container (Container:) keeps the settings it was started with.

3. Attach or stream

Reuse an existing workspace, or stream stdout while a command runs (Docker, Local, SSH):

// Attach to a container that already exists; Close does not remove it.
box := kritrim.Docker(kritrim.DockerConfig{Container: "agent-workspace"})

// Stream output while a command runs (Docker, Local, SSH).
m, _ := box.Open(ctx, kritrim.OpenConfig{})
sm := m.(kritrim.StreamingMachine)
sm.ExecStream(ctx, req, func(stdout, stderr string) { fmt.Print(stdout) })

4. Use SSH (optional)

Point at a remote host with an identity file. Host-key checking is enforced by default; extra SSH options are filtered to block directives that run local commands.

import "github.com/ganeshdipdumbare/kritrim/sandbox/ssh"

box, err := ssh.New(ssh.Config{
	Host:         "ubuntu@10.0.1.5",
	WorkingDir:   "/home/ubuntu/workspace",
	IdentityFile: "~/.ssh/agent_key",
})

The sealed agent

This guide takes you to an agent that runs entirely inside a sandbox: build a Linux box binary, configure Sealed, and let the host broker model calls, secrets, egress, approvals and audit. Provider API keys and secret values never enter the box — only the host process holds them.

1. Configure sealed mode

Same binary, two modes: inside the box it serves RPC; on the host New starts the sandbox. Set ANTHROPIC_API_KEY (or your provider's key) on the host only. Build Binary for Linux.

cfg := kritrim.Config{
	Model: kritrim.Anthropic("claude-sonnet-5-5"),
	Tools: []kritrim.Tool{kritrim.Shell(kritrim.ShellConfig{Allow: []string{"ls"}})},
	Sealed: &kritrim.Sealed{
		Sandbox:   kritrim.Docker(kritrim.DockerConfig{Image: "debian:bookworm-slim"}),
		Binary:    "./box", // GOOS=linux build
		Egress:    []string{"api.github.com"},
		Secrets:   map[string][]string{"GITHUB_TOKEN": {"api.github.com"}},
		MaxTokens: 200_000,
		Bridged:   []string{"crm_lookup"},
	},
}

if kritrim.InBox() {
	log.Fatal(kritrim.ServeBox(ctx, os.Stdin, os.Stdout, cfg))
}
a, err := kritrim.New(cfg)
What just happened

On the host, New opened the sandbox, started your Linux binary, and began brokering. Inside the box, ServeBox runs the agent loop with no API keys — every outbound call goes through the host.

2. Build the box binary

Cross-compile for the sandbox OS/arch (Docker images are usually linux/amd64):

go run ./cmd/kritrim box build -o box .
# or: GOOS=linux GOARCH=amd64 go build -o box .

3. Know what crosses the boundary

Columns: what the box requests, and what the host does in response.

The box needsThe host does
a model callchecks the token budget before the call, injects the key, calls the provider one call at a time, streams tokens back
a secret://returns a random placeholder, substitutes it only for allowed hosts, never follows a cross-host redirect with it, and redacts responses
a bridged toolruns it on the host; a risky one runs only for a call the host approved, once, with exactly the approved arguments
egressallowlist and SSRF checks on the host
an approvalasks Config.Approve on the host with a host-written message and persists the pause
an audit entrywrites it marked source: "box" with the host's identity

The box is treated as untrusted. User, roles, thread and run id come from the run the host started, never from the box. Every host capability call holds a lease on that run: when the run ends, in-flight calls are canceled and waited for, and new ones are refused.

Local is not isolation

kritrim.Local() exists for development and requires AllowUnsafeLocal: true. Use Docker or a cloud sandbox for a real boundary.

a, err := kritrim.New(kritrim.Config{

A2A

This guide takes you to Agent-to-Agent: serve one agent over A2A with bearer (or OAuth) auth, call a remote agent with the same Result type, and optionally use it as a tool or graph node. Set A2A_TOKEN (or your OAuth client credentials) before starting the server or client.

1. Serve an agent

Build a server with an agent card, auth, a per-context agent factory and a task store. Keep the bearer token in the environment — an empty token is refused.

srv, err := a2a.NewServer(a2a.ServerConfig{
	Card:  a2a.Card{Name: "Triage", Description: "Routes support tickets"},
	Auth:  a2a.Bearer(os.Getenv("A2A_TOKEN")),
	Agent: func(contextID string) (*kritrim.Agent, error) { return buildAgent(contextID), nil },
	Tasks: a2a.MemoryTasks(), // or a2a.SQLTasks(db, cfg)
	PushAllowPrivate: false,
})
if err != nil {
	log.Fatal(err)
}
http.ListenAndServe(":9000", srv)
What just happened

Callers hit the A2A endpoints with the bearer token. Each context gets an agent from your factory; tasks and push configs stay isolated per principal when you use token maps.

2. Call a remote agent

Point the client at the endpoint. Prefer secret:// in headers so the token stays in Config.Secrets on the calling side. OAuth client credentials are optional.

c, err := a2a.NewClient(a2a.ClientConfig{
	Endpoint: "https://triage.internal",
	Headers:  map[string]string{"Authorization": "Bearer secret://A2A_TOKEN"},
	// OAuth client credentials:
	TokenURL: "https://auth.example.com/token", ClientID: "id", ClientSecret: "secret",
	// Push every task to a webhook:
	PushURL: "https://app.example.com/a2a/events", PushToken: "shared",
})
res, _ := c.Run(ctx, "ticket 42")
tool := c.AsTool("triage", "Routes a ticket")

// Files: images reach the model, text files are inlined.
res, _ = c.Run(ctx, "summarize", a2a.Files(a2a.File{Name: "notes.md", MimeType: "text/markdown", Bytes: notes}))

// A remote agent as a graph node.
g, _ := multiagent.Sequence(multiagent.Step{Name: "triage", Node: c.Node()})

3. What is implemented

  • Agent card, message/send, message/stream, tasks/get, tasks/cancel.
  • Per-context agents with an LRU, text, data and file parts, and interrupt → input-required → resume.
  • File parts: images go to the model, text files are inlined in the prompt, other types are refused. A file URI is fetched only from a host in ServerConfig.FileHosts, checked at dial time, without redirects, within MaxFileBytes.
  • Push notifications with a token, and tasks/pushNotificationConfig/{set,get,list,delete}. Push URLs must be public http(s) (checked at set time and at dial time), redirects are not followed, and header values are sent as given: secret:// is never resolved on the server.
  • Bearer auth (constant-time; an empty token is refused) and OAuth client credentials.
  • Per-caller isolation: with a2a.Tokens(map[token]principal) (or any Auth that implements Principal), each task, context, conversation and push config belongs to the caller that created it. Other callers get "task not found". With a single Bearer token, all callers share one principal.
  • The client only follows redirects on the same allowed host, so its credentials stay where you sent them.

Multi-agent

This guide takes you from one agent as a tool, to a graph or swarm when the path matters, then back to a single tool for a parent agent. Each child agent uses its own model credentials the same way a solo agent does.

1. Expose an agent as a tool

Start here when the parent only needs a specialist. The parent's model sends a sentence and gets an answer — it never sees the child's loop.

expert, err := kritrim.New(kritrim.Config{Model: model, Instructions: "You are a Lisbon expert."})
main, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: []kritrim.Tool{expert.AsTool("lisbon_expert", "Answers Lisbon questions")},
})
What just happened

When the main agent called lisbon_expert, kritrim ran the expert agent to completion and returned its text as the tool result.

2. Build a graph

Use a graph when routing or multi-step control flow belongs in code, not in a tool description:

g := multiagent.NewGraph().Start("triage").
	Node("triage", triageNode).
	Node("billing", billingNode).
	Edge("triage", "billing", func(s *multiagent.State) bool { return s.Get("intent") == "billing" })

res, _ := g.Run(ctx, "invoice question")

3. Run a swarm

Members get handoff_to_<name> tools and pass work to each other:

s, err := multiagent.NewSwarm(
	multiagent.Member{Name: "researcher", Description: "finds facts", Agent: researcher},
	multiagent.Member{Name: "writer", Description: "writes", Agent: writer},
)
res, _ := s.Run(ctx, "draft the launch post")

4. Hand a composition to another agent

A whole graph or swarm can be one tool for another agent, the way Agent.AsTool hands over one agent. The caller's model never sees the nodes or the handoffs.

front, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: []kritrim.Tool{
		g.AsTool("support_desk", "Routes and answers a support ticket"),
		s.AsTool("content_team", "Researches and drafts a post"),
	},
})

5. Use Sequence and Router presets

Both build an ordinary graph you can extend, cap or hand over with AsTool. A router whose classifier names an unknown route fails the run instead of guessing.

pipeline, _ := multiagent.Sequence(
	multiagent.Step{Name: "draft", Node: multiagent.AgentNode(writer)},
	multiagent.Step{Name: "review", Node: multiagent.AgentNode(reviewer)},
)
router, _ := multiagent.Router(classify, map[string]multiagent.Node{
	"billing": multiagent.AgentNode(billing),
	"tech":    remote.Node(), // an A2A agent
})

Anything else is plain Go; there is no extra workflow primitive.

Triggers

This guide takes you to agents that wake on a schedule or a signed webhook: start a scheduler with cron or interval jobs, then verify HMAC deliveries with replay protection. Put the webhook secret in secret:// / env — never in source control.

1. Schedule runs

Pass an agent and one or more schedules. Use a shared store when several instances share the workload so each tick runs once. Errors are logged, not returned.

sched, err := trigger.NewScheduler(agent,
	trigger.Schedule{Name: "digest", Cron: "0 9 * * mon-fri", Location: berlin, Thread: "daily", Prompt: "summarize yesterday"},
	trigger.Schedule{Name: "poll", Every: 10 * time.Minute, Thread: "poll", Prompt: "check the queue"})
if err != nil {
	log.Fatal(err)
}
sched.SetStore(store) // shared by every instance: each tick runs once
sched.Start(ctx)
defer sched.Close()

Schedules take a five-field cron expression or a descriptor such as @daily, read in Location, or an Every interval aligned to the epoch so instances agree on when a tick is due. Names (default: the thread) must be unique. A schedule skips a tick when its previous run is still going.

What just happened

The scheduler started background ticks. At each due time it runs the agent with the schedule's prompt and thread, using the store to claim the tick across instances.

2. Accept a signed webhook

Resolve the shared secret from env or secret://HOOK_SECRET. The handler verifies HMAC-SHA256 over a versioned, length-prefixed encoding of the timestamp, idempotency key and body.

hook, err := trigger.Webhook(trigger.WebhookConfig{
	Agent:  agent,
	Secret: "secret://HOOK_SECRET",
})
http.Handle("/hook", hook)

// Sender side:
ts := time.Now()
req.Header.Set(trigger.TimestampHeader, strconv.FormatInt(ts.Unix(), 10))
req.Header.Set(trigger.IdempotencyHeader, "evt-123")
req.Header.Set(trigger.SignatureHeader, trigger.Sign(secret, ts, "evt-123", body))

3. Rely on replay and dedupe rules

Requests outside Tolerance (default 5 minutes) are refused. Each delivery runs once: duplicates, including concurrent ones, get the first result; a delivery without a key is identified by its signature. Reusing a key for a different body returns 409. Deliveries are remembered for DedupeTTL in a DedupeStore: trigger.MemoryDedupe(n) for one process (when full of unexpired deliveries it answers 503 with Retry-After rather than forgetting any), or trigger.SQLDedupe(db, cfg) on Postgres, SQLite or MySQL when several instances serve the webhook.

Evals

This guide takes you to a gated eval suite: define cases and evaluators, run an experiment, optionally use the CLI, then add built-in judge criteria and chaos. Judge models need their own API keys; offline cases can use the mock model.

1. Run an experiment

An experiment is cases, evaluators, optional detectors/cache, and a function that runs one case. Point Cache at a directory to skip identical work across CI runs.

report, err := evals.Experiment{
	Cases: []evals.Case{
		{Name: "capital", Input: "Capital of France?", Expected: "Paris"},
	},
	Evaluators: []evals.Evaluator{
		evals.Contains(),
		evals.ToolCalls(evals.ToolCallConfig{Require: []string{"lookup"}}),
		evals.LLMJudge(evals.JudgeConfig{Model: judge, Rubric: "1.0 if correct"}),
	},
	Concurrency: 4,
	Detect:      true,
	Cache:       evals.DirCache(".agent/evals"),
}.Run(ctx, func(ctx context.Context, c evals.Case) (*kritrim.Result, error) {
	return agent.Run(ctx, c.Input, kritrim.Thread(c.Name))
})
fmt.Print(report.Summary())
What just happened

Each case ran your agent, then every evaluator scored the result. Detectors flagged empty output, pending approvals and similar failures. The summary is what you print or fail CI on.

3. Use the CLI

kritrim-evals runs a suite without Go glue. Install from the releases page (or build from the repo). run starts your agent program once per case with the input on stdin; the program prints the answer, or a kritrim.Result as JSON to keep tool calls for trajectory checks. Every command exits 1 when a case fails.

kritrim-evals generate -model anthropic:claude-sonnet-5-5 -context agent.md -n 10 > cases.jsonl
kritrim-evals run -cases cases.jsonl -contains -detect -o report.json -- go run ./myagent
kritrim-evals traces -judge faithful,achieved -judge-model openai:gpt-4.1 trace.jsonl
kritrim-evals report report.json
kritrim-evals diagnose report.json

traces scores production traffic recorded with trace.JSON(w, trace.Content()). Set provider keys for any -model / -judge-model flags.

4. Use built-in judge criteria

Writing a good rubric is most of the work of an LLM judge. evals.Judge takes one of twelve ready-made ones. 1.0 is always good, including for safety criteria. Groups and criteria:

Evaluators: []evals.Evaluator{
	evals.Judge(evals.Faithful, judge), // every claim backed by a tool result
	evals.Judge(evals.Achieved, judge), // the task was done, not just described
	evals.Judge(evals.Harmless, judge),
}
GroupCriteria
QualityFaithful, Correct, Relevant, Coherent, Concise, Helpful
SafetyHarmless, Unbiased, Answered (did not refuse a reasonable request)
BehaviourObedient, Achieved, Recovered

Each criterion is an exported rubric string: read it, or copy it into JudgeConfig.Rubric and adapt. Judges see the trajectory, not only the final answer. A trajectory check confirms a tool was called; ToolParameters checks how:

evals.ToolParameters("refund", func(args map[string]any) error {
	if args["amount"].(float64) > 100 {
		return errors.New("refund over the ceiling")
	}
	return nil
})

5. Chaos-test recovery

A suite on a good day only proves the agent works on a good day. Chaos fails tools on purpose so you see report-success, retry-until-limit, or find-another-way. Failures are counted, not random — the same case fails the same call every time.

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: tools,
	Hooks: evals.Chaos(evals.ChaosConfig{
		Fail:    map[string]int{"http_request": 1}, // first call per run fails; "*" for every tool
		Latency: 2 * time.Second,
	}),
})
report, _ := evals.Experiment{
	Cases:      cases,
	Evaluators: []evals.Evaluator{evals.Resilient(), evals.Judge(evals.Recovered, judge)},
}.Run(ctx, run)

Resilient is the deterministic half (the run finished despite a failure); Judge(Recovered, …) asks whether what the agent did instead made sense. Check FailedTools(result) when you need proof the failure happened. Give concurrent runs a kritrim.RunID or a thread so counting stays per run.

Memory, skills and plugins

This guide takes you through long-lived knowledge and control loops: file memory (optional semantic search), progressive skills, offload/inject plugins, and a goal loop that checks the world. Semantic memory needs an embedder API key; lexical memory and skills need none.

1. Add memory tools

Create a store, expose remember / recall tools, and optionally inject top hits into the system prompt:

store, err := memory.NewFile(".agent/memory")
a, err := kritrim.New(kritrim.Config{
	Model: model,
	Tools: memory.Tools(store),                 // remember, recall
	Hooks: memory.Inject(store, 5),             // recall into the system prompt
})
What just happened

The agent can store facts and retrieve them later. Inject pulls the top matches into the system prompt each run so the model sees them without an explicit recall call.

2. Turn on semantic search (optional)

Recall is lexical by default. memory.NewSemantic adds embedding search, ranking by meaning blended with the keyword score. Set the embedder's key (OPENAI_API_KEY, Ollama local, Gemini, or Bedrock AWS credentials).

store, err := memory.NewSemantic(base, memory.OpenAIEmbedder("text-embedding-3-small"),
	memory.SemanticConfig{Dir: ".agent/memory"}) // vectors survive a restart

Embedders: OpenAIEmbedder (and any compatible API), OllamaEmbedder, GeminiEmbedder, BedrockEmbedder. No vector database; what you remember is sent to the embedding provider.

3. Load skills

Each SKILL.md under a directory keeps its body out of the prompt until the model calls use_skill:

sk, err := skills.Load("./skills")
a, err := kritrim.New(kritrim.Config{
	Model:        model,
	Instructions: "You are a support agent.\n\n" + skills.Prompt(sk),
	Tools:        append(skills.Tools(sk), kritrim.Time()),
})

4. Use plugins (offload, inject, steer)

Offload large tool results to disk and give the model a reader tool. plugin.Inject adds context; plugin.Steer adds a just-in-time user message.

hooks, readOffloaded := plugin.Offload(".agent/offload", 16_000)
a, err := kritrim.New(kritrim.Config{
	Model: model,
	Hooks: hooks,
	Tools: []kritrim.Tool{readOffloaded},
})

5. Close the loop with GoalLoop

One Run ends when the model stops calling tools — the model's judgement, not a fact. plugin.GoalLoop re-prompts the same thread until a check you write says the job is done. Thread is required so attempts share one conversation.

res, err := plugin.GoalLoop(ctx, agent, plugin.GoalConfig{
	Goal:   "go build ./... exits zero",
	Thread: "fix-build",
	Done: func(ctx context.Context, res *kritrim.Result) (bool, error) {
		return exec.Command("go", "build", "./...").Run() == nil, nil
	},
	MaxAttempts: 5, // the default
})
if errors.Is(err, plugin.ErrGoalNotMet) {
	// res is the last attempt; show it to a human
}
  • Check the world, not the transcript. A model that says the tests pass has only said so. Run the tests in Done.
  • Write the goal as a test. "every file under ./api compiles" is checkable; "fix the API" is not. Every retry prompt restates it.
  • Approvals stop the loop. Resume with kritrim.Decisions, then call GoalLoop again.

Nudge customises the retry prompt. plugin.Goal(goal) keeps the goal in the system prompt when you drive the loop yourself.

Observability

This guide takes you to signed audit logs and OTel signals: enable a hash-chained audit file, verify it, then attach tracing hooks. Keep the audit HMAC key (32+ random bytes) in a KMS — not on the same host as the log file.

1. Turn on audit

Pass an audit sink on the agent. With AuditKey every entry is chained with HMAC-SHA256 and audit.jsonl.head holds a signed record of the last entry.

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Audit: kritrim.AuditFile(".agent/audit.jsonl", kritrim.AuditKey(key)),
})
// later
if err := kritrim.VerifyAudit(".agent/audit.jsonl", kritrim.AuditKey(key)); err != nil {
	log.Fatal(err)
}

Someone who can write the file but lacks the key cannot rewrite or truncate it without VerifyAudit failing. Without a key the plain SHA-256 chain only detects accidental corruption. Ship the head to external storage to detect a rollback of both files.

Before its first append, a sink verifies the existing log with its own key and refuses to extend a log that fails. An empty key is an error, never "no signing".

What just happened

Every model call, tool call and approval appended a line. VerifyAudit walked the chain and checked the signed head.

2. Export traces, metrics and logs

Point OTLP at a collector (default local example below). No provider API key is required for export — only your collector endpoint.

a, err := kritrim.New(kritrim.Config{
	Model: model,
	Hooks: trace.OTel(trace.OTLPConfig{
		Endpoint: "http://localhost:4318",
		Service:  "support-agent",
	}),
})

trace.OTel sends OTLP/HTTP traces, metrics and logs. trace.OTLP is traces only; trace.JSON(w) writes one line per event with its run id and no conversation text. trace.JSON(w, trace.Content()) adds prompts, replies, tool arguments and results — scorable offline and as sensitive as the conversation.
